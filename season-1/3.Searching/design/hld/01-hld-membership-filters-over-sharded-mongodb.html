HLD: Membership Filters over Sharded MongoDB

Season 1 / Searching. Language independent: Java, Python, Go, Rust or Node.js can all build this.

1. Goal

  • Answer "does this key exist?" fast, and skip the database for most misses.
  • A small in-memory filter sits in front of sharded + replicated MongoDB.
  • Same design, three filters: Bloom, Cuckoo, Binary Fuse.
Filter saysMeaningAction
definitely notAlways true. No false negatives.Return "not found". Skip DB.
maybeCan be a false positive.Ask DB. DB is the truth.

5. Request flows

FlowSteps
Read key K1. Ask filter. 2. If "definitely not", return not found (no DB call). 3. If "maybe", query DB. 4. DB has it: return it. DB does not: false positive, return not found.
Write key K1. Write to DB first (majority write concern). 2. After success, filter.add(K). 3. Other workers get it from the change stream.
Delete key KDelete from DB. Cuckoo: also filter.remove(K). Bloom and Fuse: key stays as a harmless false positive until next rebuild.

Rule: DB first, filter second. A filter that says "maybe" for a missing key is fine. A filter that says "no" for an existing key is a bug.

6. Keeping 4 workers in sync

PieceHow
StartupEach worker reads all keys from DB and builds its filter. It serves traffic only after that.
Live updatesEach worker listens to a MongoDB change stream and calls add or remove.
No gapStart the change stream before the startup scan, so no key is missed.
Periodic rebuildBuild a new filter in background, swap it in one step.
Binary FuseCannot add. Keep a small delta set of new keys. Lookup checks filter OR delta set. Rebuild folds it in.
Filter fullIf Cuckoo add fails or Bloom is over capacity, rebuild bigger.

8. Failures

FailureResponse
Worker restartsRebuild filter from DB. Do not serve until ready.
Change stream breaksResume from last token. If too old, full rebuild.
Primary failsDriver retries writes. Filter unchanged.
Shard down"Maybe" answers for its keys return error. "Definitely not" still works.
